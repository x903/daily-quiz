## 一、用户名唯一性

### 1.1 规则

| 项 | 规则 | 错误码 | 提示文案 |
|---|---|---|---|
| 必填 | 不能为空 | `USERNAME_REQUIRED` | 请输入用户名 |
| 长度 | 4-20 位（按字符数） | `USERNAME_LENGTH` | 用户名长度需为 4-20 位 |
| 字符集 | 仅 `A-Z a-z 0-9 _ .` | `USERNAME_CHARS` | 用户名只能包含字母、数字、下划线或点号 |
| 非纯数字 | `12345678` 拒绝 | `USERNAME_ALL_DIGITS` | 用户名不能为纯数字 |
| 点号位置 | 不能出现在首尾，不能连续 | `USERNAME_FORMAT` | 用户名格式不正确，点号不能出现在首尾或连续出现 |
| 保留词 | admin / administrator / root / system / manager 等 26 个 | `USERNAME_RESERVED` | 该用户名属于系统保留词，请更换 |
| 唯一性 | users + admins 两表都不允许重名，大小写不敏感 | `USERNAME_TAKEN` | 该用户名已被注册，请更换 |

归一化：`strip()` + `lower()`。注册、登录、实时校验三处共用 `auth.validate_username` /
`auth.normalize_username`，不存在"前端一套、后端一套"的分叉。

### 1.2 三层校验流程

```
                     ┌───────────────────────────────┐
  用户输入用户名 ───▶ │ ① 前端 localValidate（即时）   │
                     │   长度 / 字符集 / 纯数字 / 点号 │
                     └───────────────┬───────────────┘
                                     │ 通过
                                     ▼
                     ┌───────────────────────────────┐
  失焦（blur）   ───▶ │ ② GET /api/auth/check-username │──▶ 绿色「可以使用」
                     │   服务端 validate + 查库       │──▶ 红色「已被注册 / 格式错误」
                     └───────────────┬───────────────┘
                                     │ 提交
                                     ▼
                     ┌───────────────────────────────┐
  点击注册       ───▶ │ ③ POST /api/auth/register      │
                     │   再查一次 + 捕获唯一索引冲突   │──▶ 409 USERNAME_TAKEN
                     └───────────────┬───────────────┘
                                     │ INSERT
                                     ▼
                     ┌───────────────────────────────┐
                     │ ④ DB UNIQUE INDEX 兜底         │
                     │   SQLite: NOCASE 唯一索引      │
                     │   MySQL : uk_users_username    │
                     └───────────────────────────────┘
```

第 ③ 步与第 ④ 步是并发安全的关键：两个请求可能同时通过预查询，最终由数据库唯一索引
判定胜负，`auth.register_user` 捕获 `db.IntegrityError` 后统一返回 409。

### 1.3 数据库变更

MySQL（`schema_mysql.sql` 已有，存量库由 `_migrate()` 幂等补齐）：

```sql
ALTER TABLE users ADD UNIQUE KEY uk_users_username (username);
```

SQLite（`username TEXT NOT NULL UNIQUE` 区分大小写，额外补 NOCASE 索引）：

```sql
CREATE UNIQUE INDEX IF NOT EXISTS uk_users_username
    ON users(username COLLATE NOCASE);
```

迁移顺序（`models._migrate()` 尾部）：

1. 统计 `COUNT(*)` 与 `COUNT(DISTINCT LOWER(TRIM(username)))`；
2. 两者相等时执行 `UPDATE users SET username = LOWER(TRIM(username))`，否则跳过并打印告警，
   避免把历史大写用户名改坏；
3. 建唯一索引，失败时打印「请先清理重复用户名」，不阻断启动。

### 1.4 接口

**GET `/api/auth/check-username?username=xxx`**

```json
{ "ok": true, "available": false, "username": "user",
  "code": "USERNAME_TAKEN", "message": "该用户名已被注册，请更换" }
```

限流：同 IP 60 次 / 分钟（`auth:check:{ip}`），超出返回 429。

**POST `/api/auth/register`**

```json
// 请求
{ "username": "alice_01", "password": "abc12345",
  "confirmPassword": "abc12345", "email": "a@b.com", "phone": "13900001111", "next": "/" }

// 成功 200
{ "ok": true, "data": { "user": { "id": 7, "username": "alice_01" }, "redirect": "/" } }

// 重名 409
{ "ok": false, "error": "该用户名已被注册，请更换", "code": "USERNAME_TAKEN" }
```

- `email` / `phone` 选填，给了就校验格式与唯一性，落库后标记为「未验证」，到个人中心走验证码绑定；
- 成功后直接写 session 并返回跳转地址（与表单注册行为一致）；
- `confirmPassword` 不一致返回 `PASSWORD_MISMATCH`（400）。

## 二、登录图形验证码

### 2.1 生成规则

| 项 | 取值 |
|---|---|
| 长度 | 4 位（`CAPTCHA_LENGTH`，4-6 位区间） |
| 字符池 | `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`，剔除 `I O 0 1 l` |
| 干扰 | 5 条随机干扰线 + 30 个噪点 + 每字符 ±18° 旋转 + 随机字号/颜色 |
| 格式 | 内联 SVG → `data:image/svg+xml;base64,...`，不落地图片文件 |
| 标识 | `captchaKey = secrets.token_urlsafe(18)` |
| 明文 | 只存 Redis / 服务端缓存，接口只回 `captchaKey` + `image` |
| 有效期 | 300 秒 |
| 一次性 | 校验时 `GETDEL`，无论对错都删除 |

### 2.2 登录流程

```
 ┌──────────┐   ① GET /api/auth/captcha    ┌──────────────┐
 │ 登录页   │ ───────────────────────────▶ │ 服务端        │
 │ (浏览器) │ ◀─────────────────────────── │ 生成 4 位明文 │
 └────┬─────┘   captchaKey + SVG data URI  └──────┬───────┘
      │                                           │ SETEX 300s
      │                                           ▼
      │                                    ┌──────────────┐
      │                                    │ Redis        │
      │                                    │ login:captcha│
      │                                    └──────┬───────┘
      │ ② POST /api/auth/login                    │
      │    username / password /                  │
      │    captchaKey / captchaCode               │
      ▼                                           ▼
 ┌─────────────────────────────────────────────────────────┐
 │ 服务端校验顺序                                           │
 │  0. 必填校验（用户名 / 密码）                            │
 │  1. 账号锁定？  login:lock:{username} 存在 → 423         │
 │  2. 验证码存在？ GETDEL 取不到 → 400 CAPTCHA_INVALID     │
 │  3. 验证码正确？ compare_digest（忽略大小写）→ 400       │
 │  4. 账号密码匹配？ 失败 → 记一次失败，401                │
 │  5. 成功 → 清空失败计数 → 写 session → 返回 redirect     │
 └─────────────────────────────────────────────────────────┘
```

验证码先于密码校验，因此"验证码错误"不会泄露账号是否存在；密码错误统一提示
「用户名或密码错误」，不区分「用户不存在 / 密码不对」。

### 2.3 接口

**GET `/api/auth/captcha`**

```json
{ "ok": true, "data": {
    "captchaKey": "8ElM8qg4gqQRBOK97SjDGHUS",
    "image": "data:image/svg+xml;base64,PHN2ZyB4bWxucz0i...",
    "expiresIn": 300 } }
```

限流命中：`429 { "ok": false, "code": "CAPTCHA_RATE_LIMITED", "retry_after": 243 }`

**POST `/api/auth/login`**

```json
// 请求
{ "username": "user", "password": "user123",
  "captchaKey": "8ElM...", "captchaCode": "3YYP", "next": "/daily-quiz" }

// 成功 200
{ "ok": true, "data": { "user": { "id": 2, "username": "user" }, "redirect": "/daily-quiz" } }

// 验证码错误 / 过期 400
{ "ok": false, "error": "验证码错误或已过期", "code": "CAPTCHA_INVALID",
  "captcha_required": true }

// 密码错误 401（附剩余次数）
{ "ok": false, "error": "用户名或密码错误", "code": "BAD_CREDENTIALS",
  "attempts_left": 4, "captcha_required": true }

// 账号锁定 423
{ "ok": false, "error": "登录失败次数过多，请 15 分钟后再试",
  "code": "ACCOUNT_LOCKED", "locked_seconds": 900 }
```

页面表单 `POST /login` 复用同一服务函数，隐藏域提交 `captcha_key` / `captcha_code`，
关掉 JS 也无法绕过验证码。

### 2.4 Redis 存储结构

| Key | 类型 | TTL | 值 | 用途 |
|---|---|---|---|---|
| `login:captcha:{captchaKey}` | string | 300s | 4 位明文（大写） | 验证码答案，读取即删除 |
| `login:captcha:rate:{ip}` | int | 300s | 取码次数 | 同 IP 取码限流 |
| `auth:check:{ip}` | int | 60s | 校验次数 | 用户名枚举限流 |
| `login:fail:{username}` | int | 900s | 连续失败次数 | 5 次触发锁定 |
| `login:lock:{username}` | string | 900s | 失败次数快照 | 存在即表示锁定中，TTL 即剩余锁定时长 |

- `INCR` + 首次 `EXPIRE` 用 Lua 脚本保证原子（避免 INCR 与 EXPIRE 之间进程退出导致永不过期）；
- 验证码读取用 `MULTI GET + DEL` 管道，保证"取出即删除"，多 worker 不会重复消费同一张图；
- 未配置 `REDIS_URL` 或连接失败时自动降级为进程内缓存，启动日志会明确提示
  「仅适合单实例」——gunicorn 多 worker 部署必须使用 Redis。

### 2.5 前端交互

1. 打开 `/login` 时服务端直接内联一张 SVG，首屏无额外请求；
2. 点击图片或「看不清，换一张」→ `GET /api/auth/captcha` 换新，焦点回到输入框；
3. 验证码输入框失焦做轻校验（非空、4-6 位字母数字），最终以后端为准；
4. 提交拦截 → `fetch` JSON → 按钮变「登录中…」并 disabled，防重复点击；
5. 失败：显示红字、**保留用户名与密码**、自动换一张验证码、焦点回到验证码框；
6. 成功：`location.href = redirect`（服务端已校验只允许站内相对路径）。

## 三、限流与账号临时锁定

### 3.1 阈值

| 策略 | 阈值 | 窗口 | 触发结果 |
|---|---|---|---|
| 同 IP 取验证码 | 5 次 | 5 分钟 | 429 `CAPTCHA_RATE_LIMITED` |
| 同 IP 用户名校验 | 60 次 | 1 分钟 | 429 `RATE_LIMITED` |
| 同账号连续登录失败 | 5 次 | 15 分钟 | 锁定 15 分钟，423 `ACCOUNT_LOCKED` |

阈值都可用环境变量覆盖：`CAPTCHA_RATE_LIMIT` / `CAPTCHA_RATE_WINDOW` /
`LOGIN_MAX_FAILURES` / `LOGIN_LOCK_SECONDS` / `CAPTCHA_TTL_SECONDS`。

### 3.2 状态机

```
       失败 1 次        失败 2-4 次          失败第 5 次
  ──────────────▶  ──────────────▶  ──────────────────▶  ┌──────────┐
   login:fail=1     login:fail=n       删除 fail 计数      │ 锁定 15m │
                                                        │ login:lock│
   登录成功 ──▶ 清空 fail + lock ◀──────────────────────  └────┬─────┘
                                                               │ TTL 到期
                                                               ▼
                                                          恢复正常
```

- 锁定期间即使密码正确也直接 423，不消耗验证码、不增加失败计数；
- 登录成功立即 `clear_failures`，避免"白天输错 3 次、晚上再错 2 次被锁"；
- 锁定提示不点名账号是否存在（`lock_probe` 这类不存在的用户名同样会被锁）。

### 3.3 为什么锁在缓存而不是数据库

- 锁定是短生命周期状态，TTL 天然过期，不需要定时任务清理；
- 避免恶意刷锁造成 `users` 表写放大；
- 多实例通过 Redis 共享，行为一致。

## 四、DiceBear 默认头像

- 地址：`https://api.dicebear.com/9.x/initials/svg?seed={username}&size=96&...`
- `seed` 取 `username`：同一账号永远得到同一张图，不同账号字母组合 + 背景色不同；
- 生成位置：`web_site.dicebear_avatar()`，`/profile` 与 `/api/profile/me` 共用；
- 容错：`<img onerror>` 移除图片并给容器加 `is-fallback`，回退到昵称首字母渐变块，
  外网不可达时页面仍然完整；
- `referrerpolicy="no-referrer"`：不把站内路径带给第三方。

## 七、已知取舍

1. **取码限流 5 次 / 5 分钟**按需求实现。用户连续输错验证码 5 次会被限流 5 分钟；
   若线上觉得偏严，把 `CAPTCHA_RATE_LIMIT` 调到 20 即可，代码无需改动。
2. **注册时填写未验证邮箱会占用唯一索引**。这是"注册即填邮箱"的必然代价；
   若担心被恶意占位，可在注册表单里隐藏邮箱字段，改为注册后在个人中心绑定。
3. **内存降级模式不支持多 worker**。生产必须配置 Redis（compose 已内置）；
   日志会明确打印当前后端类型。
4. **管理端验证码为后续补充**。最初需求只覆盖用户登录；现在 `/admin/login` 同样启用
   图形验证码，并与用户端做作用域隔离（见第八节），两端互不挤占额度、互不触发锁定。

## 八、管理端：验证码登录与管理员改密（补充）

### 8.1 为什么要单独一套作用域

`captcha.py` 被两端复用，但缓存键必须隔离，否则会出现两类事故：

1. 用户端签发的一张验证码可以直接拿去登管理端（跨入口重放）；
2. 有人在用户端把 `admin` 这个名字试错 5 次，会把真正的管理员锁在后台门外。

因此所有键都带 scope 前缀，默认 `user` 保持原键名不变：

| 用途 | 用户端（scope=user） | 管理端（scope=admin） |
|------|----------------------|------------------------|
| 验证码 | `login:captcha:{key}` | `admin:login:captcha:{key}` |
| 取码限流 | `login:captcha:rate:{ip}` | `admin:login:captcha:rate:{ip}` |
| 失败计数 | `login:fail:{name}` | `admin:login:fail:{name}` |
| 账号锁定 | `login:lock:{name}` | `admin:login:lock:{name}` |
| 改密原密码试错 | — | `adminpwd:login:fail:admin:{id}` |

### 8.2 登录流程

```
浏览器 /admin/login（静态页）
   │  ① GET /api/admin/captcha（no-store）
   │     └─ 同 IP 20 张 / 5 分钟；返回 captchaKey + SVG，明文只进 Redis
   │  ② 用户输入账号 / 密码 / 验证码
   ▼
POST /api/admin/login
   ├─ 必填校验                      → 400 CREDENTIALS_REQUIRED
   ├─ 账号锁定（admin:lock）          → 423 ACCOUNT_LOCKED
   ├─ 验证码（admin scope，一次性）    → 400 CAPTCHA_INVALID
   ├─ admin 表校验（status=active）   → 401 BAD_CREDENTIALS + 剩余次数
   └─ 成功：写 admin_id / admin_pwd_sig，清失败计数
```

校验顺序把验证码放在密码之前，保证「验证码错误」不会泄露管理员账号是否存在。
管理端登录页是静态 SPA，取码走接口，所以限额放宽到 20 张 / 5 分钟，
避免正常刷新页面被自己的限流挡住。

### 8.3 改密接口

| 方法与路径 | 入参 | 说明 |
|-----------|------|------|
| `POST /api/admin/password` | `old_password, new_password, confirm_password` | 修改本人密码；成功清 session，返回 `relogin=true, redirect=/admin/login?pwd=1` |
| `POST /api/admin/admins/<id>/password` | `new_password, confirm_password, operator_password` | 重置他人密码；需再次输入操作者本人密码，禁止重置自己 |

密码规则：**8-64 位、同时包含字母和数字、不含空格、不能与原密码相同**。
原密码连续错误 5 次锁 15 分钟（`adminpwd` 作用域），避免会话被劫持后反复试探。

### 8.4 会话指纹：改密即踢下线

管理端 session 里额外存 `admin_pwd_sig = sha256(password_hash)[:16]`：

- 登录成功时写入；
- 每次 `resolve_current_admin()` 都拿数据库里的当前哈希重算并比对；
- 不匹配 → 清空管理端 session，立即失效。

因此**改密或被其他管理员重置后，所有旧设备上的管理端登录自动失效**，
不需要依赖 session 过期时间，也不需要服务端 session 表。

### 8.5 验证

`python test_admin_password.py`（SQLite / MySQL 均可跑，使用一次性探针账号）：

1. 验证码接口只回 key + SVG、`Cache-Control: no-store`、TTL 300 秒；
2. 缺码 / 错码 400，正确码登录成功；
3. 用户端验证码不能登管理端，管理端验证码不能登用户端；
